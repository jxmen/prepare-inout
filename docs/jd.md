# 인아웃 — 백엔드 개발자

> 정리일: 2026-09-25

## 회사 개요

- **서비스**: 회원 300만 명, 다이어트 버티컬 플랫폼 1위
- **주요 기능**: 개인 건강 기록, AI 분석·코칭, 소셜 네트워킹, 게이미피케이션
- **현재 단계**: 출시 5년 차 B2C 서비스
  - 글로벌 서비스 확장 중
  - 본격적으로 BM을 구축한 지 1년 만에 손익분기점 돌파를 앞두고 있음
- **원하는 동료**: 빠르게 성장하는 B2C 서비스에서 문제를 현명하고 집요하게 파고드는 사람

## 직무 소개

- 사용자 기록이 안정적으로 쌓이고, 알림이 제때 닿고, AI가 기록과 맥락을 이해해 돕는 서비스를 만든다
- 글로벌 사용자까지 고려해, 새 기능을 빠르게 내놓는 속도와 기존 서비스를 안정적으로 운영하는 구조를 함께 챙긴다
- API·데이터 설계, 클라우드 인프라, 배포, 운영까지 **백엔드 전반을 맡는다**
- 필요한 일을 스스로 찾아 실행하고, 만든 기능이 사용자에게 닿을 때까지 책임진다

## 주요업무

1. **서비스 기능·백오피스 개발**: 요구사항을 구체화하고 API와 데이터 모델을 설계
2. **AI 기능 개발**: LLM API와 서비스 데이터를 연결하고, 응답 품질·처리 속도·비용을 개선
3. **데이터 처리**: 정합성을 지키고, 쿼리·인덱스·캐시를 개선해 대기 시간 단축
4. **구조 개선**: 기존 코드의 맥락을 파악해 책임과 의존성을 정리하고, 테스트로 변경 영향을 확인
5. **배포·운영**: AWS 인프라를 구성·운영하고, 배포와 반복 작업을 자동화
6. **운영 문제 해결**: 로그와 지표로 오류·성능 저하의 원인을 찾고 재발을 방지

## 자격요건

- 백엔드 개발 경력 3년 이상
- Node.js·TypeScript 기반 서비스 개발에 능숙
- 요구사항을 API와 데이터 모델로 구체화하고, **고려한 대안과 선택한 이유를 설명**할 수 있음
- RDB의 테이블·관계·인덱스를 설계하고 SQL로 데이터를 다룰 수 있음
- 클라우드 환경에서 서비스를 배포·운영하고 **실제 발생한 문제를 해결**한 경험
- AI 개발 도구를 코드 분석·구현·테스트에 활용하고, 제안된 코드와 설계를 이해·검증할 수 있음
- 모호한 요구사항을 확인하고, 제품 목적과 기술적 제약을 바탕으로 동료와 해결 방향을 논의할 수 있음

## 우대사항

- LLM 기능을 실서비스에 적용하고 응답 품질·속도·비용을 개선한 경험
- 예약 작업, 메시지 큐, 이벤트 처리 등 비동기 시스템을 개발·운영한 경험
- 기존 동작을 유지하면서 구조 개선이나 기술 전환을 진행한 경험
- 운영 지표로 DB·애플리케이션·인프라 병목을 찾아 개선하는 데 익숙함
- AI 도구나 자동화로 코드 리뷰·테스트·문서화 효율을 높인 경험

### 이 공고에서 특히 내세울 점

- **도메인이 맞음**: 칼로리 계산 사이드 프로젝트가 인아웃의 핵심 기능(식단 기록 + AI 분석)과 거의 같음. 사용자로서 이 문제를 겪어 봤다는 점을 지원 동기로 연결할 수 있음
- **백오피스**: 어드민 V2를 1인 개발해 데이터 조회 요청을 주 2~4건에서 0건으로 줄임. 주요업무 1번과 바로 맞닿음
- **BM·수익화**: 구독 결제를 처음 도입해 연 신규 매출 3,000만원 이상. 수익화 단계에 있는 회사 상황과 맞음
- **글로벌 대응**: 일할 계산의 timezone 오차를 테스트로 막은 경험. 글로벌 확장 맥락에서 언급할 만함
- **테스트·구조 개선**: 두 회사 연속으로 테스트 인프라를 처음 도입함. 주요업무 4번과 맞음

### 지원 동기 소재: 인아웃 사용 경험

- 2025년 6월: 칼로리를 찾아 입력하는 일이 불편해 LLM 칼로리 계산 웹을 직접 만듦
- 계산 결과를 인아웃에 옮겨 적기도 했지만, 수기 입력이 번거로워 인아웃을 잘 쓰지 않음
- 인아웃에 같은 기능이 유료로 출시되자 바로 결제
- 2025년 9~10월: 하루 세 끼 식단을 모두 인아웃에 기록. AI에게 다음 식단을 물어보며 식단 계획에도 활용
- **핵심 메시지**: 사용자로서 겪은 불편을 직접 풀어 봤고, 그 방향이 인아웃 팀의 방향과 같았음
  - AI 기능이 나를 잘 안 쓰던 사용자에서 매일 쓰는 유료 사용자로 바꿈. 기능의 가치를 전환으로 체감함
  - 문제를 발견하는 감각이 회사와 맞음
  - 도메인을 이해함
  - LLM 경험이 있음
- 아직 정리할 것: 직접 만든 기능과 인아웃 기능을 비교했을 때 느낀 점(정확도, 속도, 한식 인식, 입력 흐름 등)

### 보강이 필요한 것

1. **칼로리 서비스 LLM 수치화** (우선순위 1위): 비용·속도·품질 중 하나라도 개선 전후 수치를 넣기
2. **DB 인덱스·쿼리 개선 사례**: 위밋모빌리티나 나비프라에서 느린 쿼리를 인덱스로 개선한 경험이 있으면 추가
3. **운영 장애 대응 사례**: 로그·지표로 원인을 찾아 재발을 막은 경험 한 건
4. **설계 선택 이유**: 예를 들어 "Kakao 주 API + Naver fallback을 택한 이유", "트랜잭션 처리를 데코레이터로 추상화한 이유"를 한 줄씩
5. **알림 관련 경험**: JD에서 "알림이 제때 닿는" 것을 강조함. 푸시·메일 발송 경험이 있으면 추가
6. **온라인 과제 대비**: Node.js/TypeScript + RDB로 API를 설계하는 과제일 가능성이 높음. 테스트 코드와 설계 이유를 담은 README로 강점을 드러내기
